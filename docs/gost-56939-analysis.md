# Описание шкал оценки

## Шкала оценки потенциала автоматизации

| Уровень | Краткое название | Суть |
|---|---|---|
| Неавтоматизированный | None | Автоматизация проверки невозможна или экономически нецелесообразна. |
| Частичная автоматизация | Partial | Автоматизация отдельных действий и этапов проверки. Требуется участие эксперта для выполнения отдельных операций, подтверждения результатов или принятия решений. |
| Полная автоматизация | Full | Возможность автоматизировать все предусмотренные этапы проверки, включая сбор доказательств, их анализ, оценку соответствия и формирование заключения, без обязательного участия человека в каждом цикле. |

## Шкала адаптивности модулей

| Уровень адаптивности | Содержание |
|---|---|
| Статическая | Проверка выполняется по заранее заданным правилам, источникам и конфигурациям. Изменения требуют ручной актуализации настроек. |
| Ограниченная | Система обнаруживает изменения в известных источниках и компонентах, адаптирует проверки в пределах заранее определённых правил. Для существенных изменений может требоваться вмешательство человека. |
| Динамическая | Система самостоятельно обнаруживает новые компоненты и изменения инфраструктуры, определяет необходимость актуализации проверок и адаптирует их с учётом изменившейся среды в рамках установленных полномочий. |


# Вопросы
> [!NOTE]
> Возможно ли автоматически проверять регламенты на соответствие требованиям ГОСТа? Я предполагаю, что да, но в каком формате? Может быть RaC и PaC? Пока не стану добавлять в табличку
> Решение: возможно, но необходимо обсуждение формата регламента с предприятием 

> [!NOTE]
> Интересно, а как реализовать защиту самого инструмента? С точки зрения безопасности - это один из самых опасных инструментов, поскольку он будет иметь возможность просматривать, по сути, весь pipeline, включая различные разрешения, документацию и т.п.
> 
> Может стоит реализовать инструмент с точки зрения многомодульного приложения? Где есть главный оркестратор (ядро), которое управляет несколькими модулями, например один модуль на один процесс из ГОСТа. Тогда надо будет защитить и само взаимодействие между модулями и оркестратором.
> 
> Можно реализовать шифрование и подписи (mTLS), ещё можно ставить оркестратор на максимально урезанной версии ОС без определённых функций и команд. Есть ещё "защищённая очередь", из которой модуль уже сам будет забирать задачу. Тогда получается, что оркестратор не имеет прямого доступа в архитектуру модулей, а модули будут передавать JSON-результаты, формируя отчётность.
> 
> Дополнение: ядро должно знать о состоянии системы с учетом того, что надо написать не только заключение, но и рекомендации

> [!NOTE]
> Архитектурно планируется разделение на три задачи:
> 1. Сбор доказательств: поиск документов, конфигураций, логов, результатов анализаторов и данных из корпоративных систем.
> 2. Оценка доказательств: проверка полноты, актуальности, взаимосвязей и соответствия конкретным требованиям ГОСТ.
> 3. Формирование заключения: определение подтверждённых соответствий, несоответствий, недостаточности данных и рекомендаций.

### 5.1.2 Требования к реализации

#### 5.1.2.2 Выполнять периодический анализ потребностей в ресурсах, необходимых для реализации процессов разработки безопасного ПО.
**Общее обоснование:** модуль, который получает статистику от оркестратора (ядра) и выводит статистику в человекочитаемом формате для удобства контроля ресурсов. > Но последнее - это задача под звёздочкой

### 5.1.3 Артефакты реализации требований
#### 5.1.3.1 Результаты анализа текущего статуса реализации процессов разработки безопасного ПО должны содержать следующие сведения:

- результаты определения достаточности и соответствия процессов разработки безопасного ПО, реализованных разработчиком, положениям настоящего стандарта и иным стандартам, содержащим требования к разработке безопасного ПО, используемым инструментам и технологиям.
#### 5.1.3.2 Результаты анализа потребностей в ресурсах, необходимых для реализации процессов разработки безопасного ПО, могут содержать оценочные показатели в материальных и людских ресурсах для каждого реализуемого или планируемого к реализации процесса разработки безопасного ПО.
#### 5.1.3.3 План развития процессов разработки безопасного ПО должен содержать порядок (очередность) внедрения процессов разработки безопасного ПО с учетом приоритетов разработчика и имеющихся ресурсов, планируемые изменения в организационно-штатной структуре разработчика, планируемые закупки необходимых инструментов, затраты на обучение и др.
#### 5.1.3.4 План реализации процессов разработки безопасного ПО должен содержать цели, сроки и этапы внедрения процессов разработки безопасного ПО; перечень необходимых ресурсов; информацию об ответственных за внедрение процессов сотрудниках.
#### 5.1.3.5 Описание области применения процессов разработки безопасного ПО должно содержать состав ПО (версии, модули, компоненты, функциональные подсистемы и т.п.), в отношении которого должны быть реализованы процессы разработки безопасного ПО, с обоснованием выбора указанного состава ПО.

## 5.2 Обучение сотрудников

### 5.2.2 Требования к реализации

#### 5.2.2.1 Проводить анализ существующих (доступных для анализа) практик, документов, обучающих курсов и тренингов по разработке безопасного ПО.
**Обоснование:** Проверка наличия и результатов работы микросервисного модуля (сети парсеров внешних источников OWASP, NIST, БДУ ФСТЭК + ядра агрегации). Проверка наличия логов успешного выполнения Cron-задач парсеров и наличия в базе данных автоматически сформированных ежеквартальных JSON/PDF-отчетов со списками новых практик и тренингов.

#### 5.2.2.2 Разрабатывать план обучения с учетом потребностей разработчика в части используемых средств и технологий разработки.
**Обоснование:** Проверка наличия алгоритма мэтчинга стека технологий в таск-трекере или SAST-платформе. Внедрять напрямую туда, автоматика парсит манифесты проекта (pom.xml, package.json), сопоставляет их с частыми уязвимостями команды и автоматически генерирует по API персональные задачи на обучение.

#### 5.2.2.3 Проводить обучение сотрудников.
#### 5.2.2.4 Вести учет обучения сотрудников.
#### 5.2.2.5 Определить критерии пересмотра программ обучения (курсов, тренингов и т.п.).
**Общее обоснование:** Невозможно или нецелесообразно с точки зрения автоматизации

#### 5.2.2.6 Повышать осведомленность сотрудников разработчика о возможных типовых угрозах, ошибках и уязвимостях в разрабатываемом ПО, механизмах их недопущения или минимизации вероятности их возникновения, порядке сопровождения ПО и управления жизненным циклом.
**Обоснование:** Проверка наличия интеграционных плагинов безопасности (линтеров, Security Gates) внутри самого цикла разработки. Проверка наличия цифровых следов в виде выводимых интерактивных ИБ-подсказок в логах PR/MR в момент совершения разработчиком типичной ошибки.

### 5.2.3 Артефакты реализации требований
#### 5.2.3.1 Результаты анализа существующих (доступных для анализа) практик, документов, обучающих курсов и тренингов по разработке безопасного ПО с точки зрения их применимости для обучения сотрудников разработчика.
#### 5.2.3.2 План обучения, включающий:
- список сотрудников, направляемых на обучение;
- сроки прохождения обучения;
- наименование программы (курса, тренинга) обучения;
- ожидаемый результат обучения.
#### 5.2.3.3 Артефакты реализации требований, подтверждающие прохождение обучения, включают (в зависимости от учебной программы, курса) свидетельства, дипломы, отчеты обучающих платформ и иные документы и материалы, подтверждающие прохождение сотрудником обучения.
#### 5.2.3.4 Артефакты реализации требований, подтверждающие осуществление учета обучения сотрудников, должны содержать информацию о сотрудниках, прошедших обучение, пройденных программах (курсах) и результатах прохождения обучения.
#### 5.2.3.5 Критерии необходимости пересмотра программ обучения (курсов, тренингов и т.п.) должны содержать информацию о периодичности пересмотра (уточнения) программ обучения (курсов, тренингов и т.п.) или о событиях, при наступлении которых необходимо изменение программ обучения (курсов, тренингов и т.п.).
#### 5.2.3.6 Артефакты реализации требований, подтверждающие осуществление повышения осведомленности сотрудников, должны содержать информацию о проведенных мероприятиях по повышению осведомленности сотрудников о возможных типовых угрозах, ошибках и уязвимостях в разрабатываемом ПО, механизмах их недопущения или минимизации вероятности их возникновения, порядке сопровождения ПО и управления жизненным циклом, а также о сотрудниках (подразделениях), для которых проводились мероприятия по повышению осведомленности.

Проверка наличия в этих машиночитаемых правилах жестко зафиксированных технических ограничений, описывающих регламент: требований к обязательному версионированию всех типов артефактов, правил именования веток, запрета на прямое внесение изменений в обход систем контроля версий и параметров Quality Gates для проверки конфигурационных файлов.

Проверка наличия цифровых следов в виде логов успешного автоматического аудита изменений: статусов одобрения от ответственных лиц, результатов генерации и сверки SBOM, а также логов системы контроля версий (Git History), подтверждающих невозможность вливания изменений без прохождения автоматических проверок (Quality Gates) в CI/CD.

## 5.5 Управление недостатками и запросами на изменение программного обеспечения

### 5.5.2 Требования к реализации

#### 5.5.2.1 Разработать регламент управления недостатками ПО.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик безопасности как кода в репозитории управления качеством разработки. Проверка наличия в этих правилах жестко задекларированных технических требований регламента: классификации уровней критичности недостатков (багов/уязвимостей), временных лимитов на их исправление по SLA, правил автоматической эскалации и обязательных условий Quality Gates, блокирующих релиз при наличии незакрытых уязвимостей.

#### 5.5.2.2 Разработать регламент управления запросами на изменение ПО.
**Обоснование:** Проверка наличия и применения файлов конфигурации автоматических воркфлоу и политик контроля изменений в таск-трекере и репозитории инфраструктуры (IaC). Проверка наличия в этих машиночитаемых правилах жестко зафиксированных этапов согласования запросов на изменение (RFC), обязательного связывания изменений с ветками Git и автоматического контроля прохождения ревью безопасности до слияния кода.

#### 5.5.2.3 Контролировать реализацию изменений, связанных с недостатками ПО.
**Обоснование:** Проверка наличия и результатов выполнения автоматических перекрестных проверок между таск-трекером и сканерами безопасности (SAST/SCA). Автоматика запрашивает по API статус задачи по недостатку («Решено/Закрыто») и одновременно опрашивает API сканера по целевой ветке; при обнаружении в коде активных уязвимостей, задекларированных в таск-трекерах как исправленные, система немедленно генерирует сигнал ошибки и отправляет алерт на контрольную панель (систему мониторинга).

#### 5.5.2.4 Контролировать реализацию запросов на изменение в рамках жизненного цикла ПО.
**Обоснование:** Проверка наличия автоматического анализа коммитов, вошедших в релизную сборку, с помощью парсинга метаданных Git. Скрипт валидации проверяет наличие корректного ID задачи из таск-трекера в тексте коммита, соответствие статуса этой задачи в трекере («Готово к релизу») и обязательное наличие цифровых следов успешно пройденных этапов пайплайна; при обнаружении хотя бы одной ошибки или несоответствия, сборка релиза автоматически блокируется.

#### 5.5.2.5 Использовать средства автоматизации для управления недостатками и запросами на изменение разрабатываемого ПО.
**Обоснование:** Проверка наличия и контроля работоспособности интеграций средств автоматизации (Jira API, GitLab Webhooks, SonarQube API и аналоги) через непрерывный мониторинг их конфигураций. Автоматический линтер проверяет файлы конфигурации самих пайплайнов и, в случае фиксации нарушений (например, отключения шагов трекинга ошибок или удаления хуков автоматизации), немедленно блокирует PR/MR на этапе статического анализа инфраструктурного кода.

### 5.5.3 Артефакты реализации требований
#### 5.5.3.1 Регламент управления недостатками ПО должен содержать:
- порядок идентификации недостатков ПО;
- порядок управления недостатками ПО, включающий сведения о действиях, выполняемых при выявлении, устранении, тестировании, принятии решения об окончании работы с недостатком (закрытии недостатка).
#### 5.5.3.2 Регламент управления запросами на изменение ПО должен содержать:
- порядок идентификации запросов на изменение ПО;
- порядок управления запросами на изменение ПО, включающий сведения о действиях, выполняемых при осуществлении запроса на изменение, тестировании, принятии решения о закрытии запроса на изменение.
#### 5.5.3.3 Артефакты реализации требований, подтверждающие реализацию управления недостатками ПО, должны содержать зафиксированные факты изменений, связанных с недостатками, включающие следующую информацию:
- уникальный идентификатор недостатка ПО;
- описание недостатка ПО;
- версию ПО (модуля ПО, компонента ПО), к которому относится недостаток ПО;
- приоритет выполнения действий с недостатком ПО;
- текущий статус обработки изменений, связанных с недостатками ПО.
#### 5.5.3.4 Артефакты реализации требований, подтверждающие реализации управления запросами на изменение ПО, должны содержать следующую информацию:
- уникальный идентификатор запроса на изменение ПО;
- краткую характеристику запроса на изменение ПО;
- версию ПО (модуля ПО, компонента ПО), к которому относится запрос на изменение;
- приоритет выполнения действий с запросом на изменение ПО;
- текущий статус обработки запроса на изменение ПО.

## 5.6 Разработка, уточнение и анализ архитектуры программного обеспечения

### 5.6.2 Требования к реализации

#### 5.6.2.1 Определить требования безопасности к принципам проектирования архитектуры ПО, направленным на снижение количества возможных недостатков в разрабатываемом ПО.
**Обоснование:** Невозможно или нецелесообразно с точки зрения автоматизации. Аудит может сводиться лишь к ручной проверке наличия утвержденного архитектурного фреймворка или высокоуровневых политик ИБ.

Автоматический скрипт-парсер проверяет факт физического присутствия этих файлов в ветке инициализации проекта, валидирует их синтаксис и контролирует заполненность обязательных структурных разделов (описание компонентов, сетевых стыков, ролевых моделей) по эталонному JSON-шаблону.

#### 5.6.2.3 Установить критерии необходимости уточнения архитектуры ПО.
**Обоснование:** Проверка наличия конфигурационных файлов политик (PaC), описывающих цифровую структуру критериев и триггеров пересмотра архитектуры. Проверка наличия и работоспособности автоматического сбора метрик в системах визуализации (Grafana, Kibana, SonarQube), отслеживающих пороговые значения технического долга, появление новых внешних интерфейсов или превышение лимитов сложности кода (Cyclomatic Complexity), которые служат автоматическими индикаторами необходимости актуализации архитектуры.

#### 5.6.2.4 Выполнять уточнение архитектуры ПО в процессе разработки кода и его изменений с установленной периодичностью или при наступлении определенных событий.
**Обоснование:** Проверка наличия цифровых следов планового пересмотра через API таск-трекера путем валидации обязательных задач на архитектурный анализ в каждом закрытом спринте. Проверка событийного уточнения архитектуры за счет контроля скорости реагирования на инциденты: автоматика сопоставляет по API дату фиксации архитектурной уязвимости в SIEM/VM с датой создания и прохождения MR, содержащего изменения в файлах Diagrams as Code и IaC-манифестах.

### 5.6.3 Артефакты реализации требований
#### 5.6.3.1 Требования к принципам проектирования архитектуры ПО должны содержать информацию, позволяющую на начальном этапе проектирования ПО получить представление о принятых подходах и принципах проектирования архитектуры ПО (например, инкапсуляция, уникальность, разделение задач, применение заимствованных компонентов и т.п.), в том числе с точки зрения безопасности («нулевое доверие», «протоколирование событий», «резервное копирование», «формирование перечня недопустимых событий», «приоритетное использование языков с безопасной моделью памяти» и т.п.).
#### 5.6.3.2 Описание архитектуры ПО должно включать, как минимум, следующую информацию:
- назначение ПО и сценарии его использования;
- описание среды функционирования;
- ограничения и указания по применению;
- проект ПО на уровне подсистем (модулей), включающий описание их назначения, структуры, особенностей реализации, применяемых языков программирования, взаимодействия друг с другом и другим ПО с указанием соответствующих интерфейсов, сетевых портов, протоколов.
#### 5.6.3.3 Критерии необходимости уточнения архитектуры ПО должны содержать информацию о периодичности пересмотра (уточнения) архитектуры ПО в процессе разработки ПО или о событиях, при наступлении которых необходимо уточнять архитектуру ПО.
#### 5.6.3.4 Архитектура ПО, уточненная по результатам выполнения требований 5.6.2.4, должна содержать информацию об особенностях реализации ПО в процессе разработки ПО, принятых решениях по корректировкам архитектурных решений в процессе разработки, в том числе связанных с безопасностью, и причинах, их вызвавших.

## 5.7 Моделирование угроз и разработка описания поверхности атаки

### 5.7.2 Требования к реализации

#### 5.7.2.1 Выполнить первичное моделирование угроз для ПО (разработать модель угроз ПО); для выявленных угроз безопасности информации составить перечень мер по их нейтрализации (снижению вероятности возникновения).
**Обоснование:** Проверка наличия обязательных цифровых артефактов моделирования угроз в репозитории проекта или на специализированном ИБ-портале. Автоматика опрашивает API систем контроля версий или баз данных ИБ на факт физического присутствия утвержденных файлов модели угроз и связанных матриц компенсирующих мер (например, файлов threat_model.json или экспортированных отчетов), валидируя их обязательное заполнение и привязку к идентификаторам разрабатываемых эпиков/компонентов.

#### 5.7.2.2 Выполнить первичное описание поверхности атаки.
**Обоснование:** Проверка наличия структурированного конфигурационного файла описания поверхности атаки в репозитории проекта (например, attack_surface.json), валидация его минимально допустимого размера и наполнения (наличие описания портов, эндпоинтов, сетевых протоколов). Проверка работоспособности дифференциального анализа, который автоматически блокирует сборку или слияние кода, если в инфраструктурных манифестах (IaC/Terraform/Kubernetes) зафиксировано появление нового элемента сети или открытого порта, а файл описания поверхности атаки при этом не изменялся.

#### 5.7.2.3 Сформировать перечень целей (функциональных подсистем, модулей (компонентов) ПО и их интерфейсов) для проведения дальнейших исследований безопасности ПО (например, фаззинг-тестирования) с учетом архитектуры ПО, результатов моделирования угроз и выполнения анализа поверхности атаки.
**Обоснование:** Проверка наличия артефактов в виде конфигурационных файлов целей (например, профилей фаззинга, манифестов fuzz.yaml, схем openapi.yaml или списков targets.json), описывающих интерфейсы для тестирования. Проверка наличия и результатов выполнения автоматической сверки покрытия кода (Code Coverage), сопоставляющей список доступных в приложении эндпоинтов (выгруженных из кода при сборке) с перечнем задекларированных целей для фаззинг-тестирования в пайплайне, что исключает пропуск новых интерфейсов без проведения проверок ИБ.

#### 5.7.2.4 Выполнять уточнение модели угроз ПО для изменяемого в ходе разработки ПО кода с установленной периодичностью или при наступлении определенных событий.
**Обоснование:** Проверка наличия и верификации файлов моделирования угроз, преобразованных в машиночитаемый формат концепции Моделирование угроз как код (Threat-Modeling-as-Code, например, через утилиты OWASP Threat Dragon, pytm, или файлы threatmodel.yaml в Git). Автоматический скрипт выполняет парсинг этих файлов на наличие определенных маркеров и версий безопасности по расписанию (Cron) или по триггерным событиям, параллельно проверяя через API таск-трекера наличие связанных задач на пересмотр угроз и их успешные финальные статусы.

#### 5.7.2.5 Выполнять уточнение описания поверхности атаки для изменяемого в ходе разработки ПО кода с установленной периодичностью или при наступлении определенных событий.
**Обоснование:** Аналогично 5.7.2.3. Проверка наличия конфигурационных файлов целей и сопоставление изменений в исходном коде приложения с изменениями в описании поверхности атаки на регулярной плановой основе или по триггерным событиям коммитов в инфраструктурные файлы, с автоматическим контролем полноты покрытия интерфейсов тестами безопасности.

#### 5.7.2.6 При уточнении описания поверхности атаки выполнять анализ поверхности атаки методом идентификации интерфейсов ПО.
**Обоснование:** Проверка записей логов сборки (Build/CI Logs) и отчетов автоматических утилит сканирования портов и API-эндпоинтов (например, линтеров OpenAPI, инструментов OWASP ZAP, Nmap/Masscan джоб), запущенных в пайплайне для автоматической идентификации всех реально поднятых интерфейсов ПО. Проверка отсутствия критических алертов от систем мониторинга сетевого контура, подтверждающая, что в собранном артефакте не обнаружено скрытых, незадокументированных или лишних локальных и сетевых сокетов взаимодействия.

#### 5.7.2.7 Уточнять перечень целей (функциональных подсистем, модулей (компонентов) ПО и их интерфейсов) для проведения дальнейших исследований безопасности ПО (например, фаззинг-тестирования) с учетом уточненной архитектуры ПО, результатов моделирования угроз и выполнения анализа поверхности атаки для разработанного кода ПО.
**Обоснование:** Проверка одновременного присутствия изменений (изменения метаданных и коммитов в одной связке) как в файлах исходного кода/архитектуры приложения, так и в конфигурационных файлах, описывающих цели для тестирования безопасности (например, словари и структуры для фаззинга). Проверка наличия подтверждающих цифровых следов - логов успешного выполнения фаззинг-тестов (Fuzzing Job Trace) по обновленным целям с нулевым количеством падений (Crashes) на новых сетевых интерфейсах.

### 5.7.3 Артефакты реализации требований
#### 5.7.3.1 Модель угроз должна включать совокупность угроз безопасности, актуальных для разрабатываемого ПО. Каждая угроза безопасности представляется в виде совокупности свойств (характеристик), включающей, как минимум, краткое описание угрозы, предполагаемый объект воздействия и возможные последствия реализации угрозы.
#### 5.7.3.2 Перечень мер по нейтрализации (снижению вероятности возникновения) угроз безопасности информации содержит перечень необходимых действий (доработок ПО, иных мер). Перечень мер по нейтрализации (снижению вероятности возникновения) угроз безопасности информации должен быть приоритизирован с точки зрения критичности возможного ущерба от реализации угроз безопасности информации.
#### 5.7.3.3 Описание поверхности атаки должно включать совокупность потенциальных областей воздействия на информационную (автоматизированную) систему с использованием разрабатываемого ПО, которые могут быть использованы нарушителем для проведения компьютерной атаки. Описание поверхности атаки может быть частью модели угроз.
#### 5.7.3.4 Перечень целей должен включать список функциональных подсистем, модулей (компонентов) ПО и их интерфейсов, составляющих поверхность атаки, подлежащих дополнительному анализу с точки зрения безопасности.
#### 5.7.3.5 Модель угроз, уточненная по результатам выполнения требований 5.7.2.4, должна дополнительно (в случае применимости) содержать угрозы безопасности ПО, актуальные для выполненных изменений.
#### 5.7.3.6 Описание поверхности атаки, уточненное по результатам выполнения требований 5.7.2.5, должно включать перечень функциональных подсистем, модулей (компонентов) ПО и их интерфейсов, составляющих поверхность атаки, актуальных для разработанного кода ПО.
#### 5.7.3.7 Перечень целей, уточненный по результатам выполнения требований 5.7.2.7, для проведения дальнейших исследований безопасности ПО должен содержать описание функциональных подсистем, модулей (компонентов) ПО, их интерфейсов, для которых предполагаются дальнейшие исследования в части безопасности при реализации других процессов разработки безопасного ПО.

**Обоснование:** Проверка наличия и применения файлов конфигурации политик безопасности и стилей кода (например, правил для SonarQube, Semgrep, Checkmarx) в репозитории проекта. Проверка наличия цифровых следов высокого уровня покрытия автоматизацией - близкого к 100% процента сборок и релизов, успешно прошедших шаги статического анализа кода (SAST/Linting) в CI/CD пайплайнах. Проверка наличия в истории MR/PR реальных фактов блокировки пайплайнов и запрета слияния кода при нарушении правил безопасного кодирования, что служит прямым доказательством практической применимости и неотвратимости регламента.

#### 5.8.2.4 При разработке ПО рекомендуется использовать программные средства автоматической проверки правил кодирования.
**Обоснование:** Проверка наличия и обязательного запуска программных средств автоматической проверки кода - шагов линтеров и форматтеров (например, ESLint, Pylint, Black, Checkstyle) в конфигурационных файлах пайплайнов (.gitlab-ci.yml, Jenkinsfile). Проверка наличия в корне проекта файлов конфигурации данных утилит (.eslintrc, pyproject.toml), а также цифровых следов в виде успешно сформированных отчетов о сканировании и логов CI/CD (Job Logs) с нулевым количеством критических ошибок форматирования и базовых правил кодирования.

- примеры опасных и безопасных конструкций для используемых языков программирования;
- область применения правил кодирования;
- порядок проверки выполнения правил кодирования для вносимых изменений в исходный код ПО;
- рекомендации разработчиков языков программирования по использованию стандартов кодирования (языков программирования, в том числе собственной разработки), принятые разработчиком ПО.

Проверка наличия в этих машиночитаемых правилах жестко зафиксированных технических требований и параметров, описывающих регламент экспертизы: обязательного количества экспертов для проверки (например, правила Code Owners), списков проверяемых директорий, условий назначения повторного ревью и автоматической блокировки слияния кода при отсутствии согласования.

#### 5.9.2.2 Проводить экспертизу исходного кода ПО.

**Обоснование:** Проверка наличия конфигурационных файлов систем автоматической экспертизы кода (например, правил для SAST-инструментов, ИБ-линтеров или ботов автоматического ревью). Проверка настроек защиты MR/PR, подтверждающих интеграцию средств автоэкспертизы с системой контроля версий: наличие активных ИБ-виджетов безопасности, автоматических комментариев с результатами сканирования от ИБ-бота непосредственно в ветке обсуждения, а также защитных правил (Branch Protection Rules), триггеринг которых блокирует слияние кода до получения успешных логов и статусов от систем автоматического анализа.

- перечень необходимых изменений;
- вопросы к частям кода, экспертиза которых затруднена и требует дополнительных разъяснений;

## 5.10 Статический анализ исходного кода

### 5.10.2 Требования к реализации

#### 5.10.2.1 Разработать регламент проведения статического анализа исходного кода ПО.
**Обоснование:**  Проверка наличия и применения файлов конфигурации политик безопасности и качества как кода (PaC / Quality Gates, например, правил OPA Rego, глобальных настроек SonarQube Quality Gates, конфигураций Semgrep/Checkmarx) в репозитории управления качеством. Проверка наличия в этих машиночитаемых файлах жестко зафиксированных параметров, описывающих регламент: перечня обязательных для поиска типов уязвимостей (SQLi, XSS, RCE), пороговых значений плотности дефектов, критериев автоматической блокировки сборки при обнаружении критических ошибок (Severity: Critical/High) и правил разбора ложных срабатываний.

#### 5.10.2.2 Определить инструменты статического анализа для каждого используемого в ПО языка программирования.
**Обоснование:** Проверка наличия и результатов выполнения автоматических скриптов идентификации языкового стека (например, утилиты Linguist, cloc или API Git-системы), сканирующих состав репозитория. Проверка работоспособности системы автоматического контроля (Compliance Gates), которая сопоставляет обнаруженные языки программирования с матрицей соответствия (язык - инструмент) и автоматически блокирует прохождение пайплайна при отсутствии в конфигурации сборочной линии необходимых SAST-сканеров.

#### 5.10.2.3 Определить конфигурацию и параметры настройки инструментов статического анализа.
**Обоснование:** Проверка наличия и применения эталонных шаблонов конфигураций и конфигурационных файлов конкретных сканеров (.sonarproject.properties, .semgrep.yaml) в корне проекта. Автоматический аудит на отсутствие несанкционированных исключений: проверка, что критические директории с исходным кодом не добавлены в списки игнорирования (отсутствие скрытия уязвимостей), уровни критичности правил не занижены, а сам сканер использует актуальную версию набора правил (Rule-set) без локальных ослаблений, с автоматической блокировкой пайплайна при обнаружении любых нарушений.

#### 5.10.2.4 Проводить статический анализ с использованием инструментов статического анализа с регистрацией всех предупреждений о потенциальных ошибках, полученных по результатам работы инструментов статического анализа.
**Обоснование:** Проверка наличия физически сохраненных структурированных файлов отчетов (SARIF, JSON, XML) в хранилище артефактов сборки для каждого выполненного пайплайна. Проверка наличия записей обо всех найденных предупреждениях в централизованной базе данных VM или SAST-платформы (SonarQube, DefectDojo) с жесткой привязкой к уникальному ID сборки и сохранением полной истории находок. Проверка логов выполнения сканера на отсутствие флагов ручной фильтрации, подавления предупреждений или явного игнорирования дефектов на этапе самого сканирования.

#### 5.10.2.5 Осуществлять пересмотр конфигурации и параметров настройки инструментов статического анализа при выполнении установленных событий (изменениях в правилах сборки, применяемых статических анализаторах, получении информации об уязвимостях и т.п.).
**Обоснование:** Проверка наличия цифровых следов изменений в репозитории конфигураций SAST, где в тексте коммита зафиксирована связь с триггерным событием. Проверка наличия системных логов изменения версий профилей качества (Quality Profiles) на SAST-платформе с фиксацией даты, автора и списка добавленных правил. Проверка наличия закрытых задач в таск-трекере на пересмотр конфигураций, к которым через Webhook автоматически прикреплены ссылки на коммиты с обновленными правилами, и автоматическая блокировка Compliance Gates при отсутствии таких связей после мажорных событий.

#### 5.10.2.6 Осуществлять повторный статический анализ ПО после устранения ранее выявленных ошибок и уязвимостей; внесения изменений в ходе разработки в исходные тексты ПО; изменения используемых версий компиляторов, сред выполнения (для компилируемого в промежуточное представление или интерпретируемого кода), обновлений используемых инструментов статического анализа.
**Обоснование:** Проверка наличия уникального ID отчета SAST для каждого коммита и настроек принудительного запуска анализа (on: push, on: pull_request) при любом изменении исходного кода. Проверка наличия в конфигурации CI/CD триггеров повторного запуска SAST при изменении файлов описания среды (манифестов компиляторов, Dockerfile, go.mod, pom.xml) или обновлении версий самого инструмента анализа. Проверка включения обязательных проверок статуса в Git-платформе, блокирующих слияние веток до получения успешного результата сканирования, а также автоматическая фиксация изменения статусов ранее выявленных уязвимостей на «Устранено».

### 5.10.3 Артефакты реализации требований
#### 5.10.3.1 Регламент проведения статического анализа исходного кода ПО должен содержать следующие сведения:
- обязанности сотрудников и их роли при проведении статического анализа;
- критерии выбора инструментов статического анализа;
- критерии выбора ПО (модулей ПО, компонентов ПО, функциональных подсистем ПО), подлежащих проведению статического анализа;
- правила обработки срабатываний средств статического анализа;
- типы и критичность ошибок (уязвимостей), выявляемых статическим анализатором, подлежащих устранению, и приоритеты устранения ошибок (уязвимостей);

#### 5.10.3.2 Перечень инструментов статического анализа должен включать наименования инструментов статического анализа, их версии и информацию о соответствии используемым языкам программирования.
#### 5.10.3.3 Конфигурации и параметры настройки инструментов статического анализа должны обеспечивать выполнение требований регламента проведения статического анализа в части выявления типов и критичности ошибок (уязвимостей), периодичности проведения статического анализа или событий, при наступлении которых необходимо выполнять повторный статический анализ.
#### 5.10.3.4 Отчеты по результатам проведения статического анализа должны включать:
- срабатывания инструментов статического анализа;
- результаты анализа (разметки) выявленных ошибок (срабатываний статического анализатора).
#### 5.10.3.5 Конфигурации и параметры настройки инструментов статического анализа, уточненные по результатам выполнения требований 5.10.2.5, должны обеспечивать выполнение требований регламента проведения статического анализа в части выполнения критериев их пересмотра.

## 5.11 Динамический анализ кода программы

### 5.11.2 Требования к реализации

#### 5.11.2.1 Разработать регламент проведения динамического анализа кода ПО.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик безопасности и качества как кода (PaC / Quality Gates, например, правил OPA Rego, глобальных настроек DAST/Fuzzing политик в DefectDojo или GitLab CI Compliance Frameworks) в репозитории управления качеством. Проверка наличия в этих машиночитаемых файлах жестко зафиксированных параметров, описывающих регламент динамического анализа и фаззинга: требований к глубине покрытия интерфейсов, перечня обязательных для поиска типов уязвимостей времени выполнения, критериев автоматической блокировки сборки при падении тестов (Error Rate / Crashes) и правил обработки ложных срабатываний.

#### 5.11.2.2 Определить инструменты динамического анализа и фаззинг-тестирования, порядок их применения.
**Обоснование:** Проверка наличия файлов конфигураций для запуска фаззинга и настроек DAST-сканеров. Наличие зарегистрированных профилей инструментов динамического анализа для каждого проверяемого репозитория, где детально описаны версии утилит и параметры их вызова. Парсинг конфигурации пайплайна в CI/CD логах.

#### 5.11.2.3 Определить перечень модулей (компонентов) ПО, которые необходимо подвергнуть динамическому анализу, включая фаззинг-тестирование.
**Обоснование:** Проверка наличия машиночитаемого документа (.json) с перечнем компонентов. Анализ структуры проекта и сопоставление с поверхностью атаки из п. 5.7.2.5. Проверка перечня целей и конфигурации самих фазеров с последующим вердиктом (блокировкой пайплайна или пропуском на следующий этап).

#### 5.11.2.4 Определить сценарии проведения тестирования для каждого исследуемого модуля (компонента) ПО средствами динамического анализа, включая инструменты проведения фаззинг-тестирования.
**Обоснование:** Проверка наличия в кодовой базе проекта валидных файлов сценариев, которые обновляются по мере изменения самих модулей. Успешных записей компилятора, подтверждающих сборку исполняемых файлов сценариев. Явные флаги запуска сканеров с указанием кастомных сценариев в логах запуска инструментов.

#### 5.11.2.5 Проводить динамический анализ с использованием инструментов динамического анализа.
**Обоснование:** Проверка наличия лог-файлов успешной отработки инструмента (например, время отработки, обход задекларированных интерфейсов). Блокировка релиза в случае пропуска шага динамического тестирования или некорректного завершения. 

#### 5.11.2.6 Проводить повторный динамический анализ модулей (компонентов) ПО с целью контроля устранения ошибок.
**Обоснование:** Проверка наличия закрытых обнаруженных ранее уязвимостей в таск-трекерах системной учётой (автоматизированным средством проверки CI/CD). Наличие соответсвующих логов запуска инструментов DAST с указанием конкретного контекста, где ранее была зафиксирована ошибка. Активное правило запрета закрытия MR без обязательного успешного прозождения шага с DAST-сканированием.

#### 5.11.2.7 Проводить фаззинг-тестирование.
**Обоснование:** Проверка наличия успешного выполнения шагов пайплайна фаззинг-тестирования с генерацией файлов конфигурации запуска, наличия детальных отчётов по каждому запуску, наличия автоматически создаваемых записей при обнаружении аварийных завершений программы. 

#### 5.11.2.8 При проведении фаззинг-тестирования использовать тестовые коллекции входных данных, подлежащие дальнейшим мутациям, для каждого из подвергаемых фаззинг-тестированию модуля (компонента) ПО (при использовании инструментов выполнения фаззинг-тестирования, использующих коллекции входных данных), вызывающие использование различных функциональных возможностей тестируемого модуля (компонента) ПО.
**Обоснование:** Проверка наличия в хранилищах (Git, S3) структурированных директорий с файлами примеров для каждого фаззинг-харнесса (например, libFuzzer). Наличия флагов, указывающих на чтение и запись корпуса в логах фаззера.

#### 5.11.2.9 Устранять выявленные в процессе динамического анализа, включая фаззинг-тестирование, ошибки в соответствии с принятыми процедурами устранения найденных средствами динамического анализа ошибок.
**Обоснование:** Проверка наличия закрытых уязвимостей в таск-трекерах, созданных ранее на этапах DAST, Fuzz-анализов. Проверка наличия автоматических Compliance Gates с блокировкой пайплайна при наличии открытых задач с критичностью выше установленного порога. Наличие автоматических записей о закрытии уязвимостей динамического анализа с фиксацией ID коммита, в котором было внесено исправление.

#### 5.11.3.1 Регламент проведения динамического анализа кода ПО должен содержать следующие сведения:

## 5.13 Обеспечение безопасности сборочной среды программного обеспечения

### 5.13.2 Требования к реализации

**Обоснование:** Проверка наличия и применения конфигурационных файлов политик ИБ инфраструктуры как кода (IaC, PaC, например, правил Ansible-Lint, TFLint, Checkov или политик Kubernetes) в репозитории управления сборочным контуром. Проверка наличия в этих правилах жестко зафиксированных технических ограничений безопасности среды: требований к сетевой изоляции раннеров (Network Policies), запрета на запуск контейнеров от привилегированного пользователя (Rootless), параметров шифрования дисков и правил контроля целостности хостов.

#### 5.13.2.2 Зафиксировать описание ожидаемых результатов сборки ПО, прав доступа к среде сборки ПО и хранилищу результатов сборки ПО и ролей пользователей, участвующих в процессе сборки ПО.
**Обоснование:** Проверка артефактов на наличие нарушений (нет жёстко прописанных путей к результату выполнения), ролей и прав доступа (срванение реальных списков прав из систем с документальным эталоном из Git, нет случайных учёток). Наличие успешных логов ежедневного сканирования.

#### 5.13.2.3 Разработать схему сборочной среды.
**Обоснование:** Сверка схемы с реальной сборочной средой и проверка наличия и обновляемости этой схемы. 

#### 5.13.2.4 Обеспечивать регистрацию всех выполняемых действий при сборке ПО в журналах аудита; журналы аудита должны храниться способом, обеспечивающим их целостность; сроки хранения журналов аудита должны быть зафиксированы в регламенте обеспечения безопасности сборочной среды.
**Обоснование:** Проверка наличия непрерывного потока новых логов в SIEM. Наличия флагов защищённости архивных логов в хранилищах (например, `Retention: Enabled`). Автоматической проверки, что Diff между задекларированным сроком хранения логов и реальными конфигурационными параметрами баз данных/хранилищ равен нулю.

#### 5.13.2.5 Обеспечивать хранение результатов сборки ПО в выделенном хранилище — хранилище результатов сборки ПО.
**Обоснование:** Проверка наличия файлов конфигураций CI/CD пайплайнов, сборочных манифестов, а также сетевые политики и настройки реестров артефактов.

#### 5.13.2.6 Обеспечивать повторяемость сборки ПО (если применимо).
**Обоснование:** Проверка наличия файлов фиксации зависимостей (lock-файлов) в репозитории и параметры манифестов сборки, подтверждающие блокировку версий компонентов. Наличие тестового лога или артефакта (Diff Report) из CI/CD, содержащего пустой вывод команды сравнения хэшей или бинарников двух тестовых сборок одного коммита.

#### 5.13.2.7 Обеспечивать управление доступом к среде сборки ПО и хранилищу результатов сборки ПО на основе ролей пользователей.
**Обоснование:** Проверка наличия ролевых моделе (RBAC), списков пользователей, сервисных аккаунтов и их привилегий в CI/CD-системе (GitLab Runners/Projects, Jenkins) и в хранилище артефактов (Nexus, Harbor, Artifactory).

#### 5.13.2.8 Обеспечивать защиту каналов связи с внешними источниками данных для обеспечения конфиденциальности информации, обрабатываемой в сборочной среде.
**Обоснование:** Проверка наличия и обязательного использования защищенных протоколов передачи данных во всех конфигурационных файлах сборочной среды, настройках пакетных менеджеров (pom.xml, npmrc, pip.conf) и параметрах подключения к внешним репозиториям. Проверка наличия TLS/SSL-сертификатов корпоративного удостоверяющего центра на сборочных раннерах, включенных флагов проверки сертификатов (отсутствие параметров типа --insecure или strict-ssl=false) и конфигураций прокси-серверов, блокирующих незашифрованный HTTP-трафик наружу.

### 5.13.3 Артефакты реализации требований
#### 5.13.3.1 Регламент обеспечения безопасности сборочной среды должен содержать, как минимум, следующие сведения:
- обязанности сотрудников и их роли при проведении сборок ПО;
- порядок регистрации событий безопасности при реализации сборок ПО в журналах аудита;
- сроки хранения журналов аудита;
- описание мер безопасности, необходимых для реализации в сборочной среде.
#### 5.13.3.2 Информация о безопасности сборочной среды должна содержать:
- описание ожидаемых результатов сборки ПО;
- описание прав доступа к сборочной среде и хранилищу результатов сборки ПО, а также ролей пользователей, участвующих в процессе сборки ПО.
#### 5.13.3.3 Схематическое изображение сборочной среды должно содержать:
- элементы сборочной среды (серверы, узлы, виртуальные узлы, элементы среды контейнеризации и т.п.);
- связи между элементами сборочной среды, позволяющие отследить порядок (очередность) выполнения сборочных действий;
- компоненты сборочной среды, реализующие отдельные функции, в том числе меры безопасности (средства защиты информации, инструменты статического анализа и др.).
#### 5.13.3.4 Журналы аудита процессов сборки ПО должны содержать следующую информацию:
- дату и время начала и завершения сборки ПО;
- информацию о версии собираемого ПО (модуля ПО, компонента ПО);
- информацию об используемой конфигурации сборки ПО;
- информацию о шагах сборки ПО;
- информацию о событиях безопасности в соответствии с регламентом обеспечения безопасности сборочной среды.
#### 5.13.3.5 В качестве артефакта реализации требований, подтверждающих хранение результатов сборки ПО в выделенном хранилище, может использоваться журнал аудита сборки ПО, в котором указано место сохранения собранного модуля (компонента) ПО, результаты контрольного суммирования файлов, скачанных из хранилища результатов сборки ПО, и последующего сравнения их с контрольными суммами, указанными в журнале аудита сборки ПО или в графическом интерфейсе системы хранения результатов сборки ПО.
#### 5.13.3.6 В качестве артефактов реализации требований, подтверждающих повторяемость сборки ПО, могут использоваться журналы аудита выполненных сборок, сравненные друг с другом; результаты контрольного суммирования файлов, полученных при разных запусках сборок, и последующего их сравнения (по контрольным суммам, по бинарному представлению, по наименованию и размеру и др.).

## 5.14 Управление доступом и контроль целостности кода при разработке программного обеспечения

### 5.14.2 Требования к реализации

#### 5.14.2.1 Разработать регламент доступа к исходному коду ПО и обеспечения его целостности.
**Обоснование:** Проверка наличия и применения конфигурационных файлов глобальных политик безопасности организации в системе контроля версий (например, JSON/YAML манифестов настроек групп в GitLab/GitHub, проверяемых скриптами соответствия, или правил OPA Rego). Проверка наличия в этих машиночитаемых файлах жестко задекларированных технических правил регламента: требований к обязательной двухфакторной аутентификации (2FA), запрета на публичный доступ к корпоративным репозиториям, глобальных политик защиты веток (Branch Protection Policies) и обязательного использования GPG/SSH ключей для подписи коммитов.

#### 5.14.2.2 Осуществлять управление доступом к исходному коду ПО на основе выбранной модели управления доступом.
**Обоснование:** Проверка наличия и корректности настроек ролевой модели доступа в системе контроля версий на уровнях организации, групп и отдельных репозиториев. Проверка списков активных пользователей, учетных записей внешних подрядчиков и сервисных аккаунтов, а также политик защиты веток (Protected Branches), ограничивающих права на слияние (Merge) и прямую запись (Push) кода в master/main ветки только для авторизованных ролей. Проверка наличия результатов автоматической сверки (Diff) текущих прав доступа со списками актуальных сотрудников из кадровых систем (LDAP/Active Directory) для своевременного обнаружения и блокировки бесхозных учетных записей.

#### 5.14.2.3 Осуществлять контроль целостности собственного исходного кода.
**Обоснование:** Проверка наличия и обязательного использования политик подписи коммитов и включения флага обязательной проверки подписей (Signed Commits Required) в настройках репозиториев. Проверка наличия в истории изменений цифровых следов валидации - статусов верификации подписи, а также сквозного контроля хеш-сумм файлов исходного кода, зафиксированных в коммитах, для исключения фактов несанкционированного изменения кода в обход системы контроля версий.

### 5.14.3 Артефакты реализации требований
#### 5.14.3.1 Регламент доступа к исходному коду ПО и обеспечения его целостности должен содержать следующие сведения:
- обязанности сотрудников, их права и роли при разработке ПО;
- правила хранения исходного кода ПО, включая правила резервного копирования исходного кода ПО;
- правила внесения изменений (модификации, добавления, удаления) в исходный код ПО;
- критерии выбора способов и инструментов контроля целостности ПО;
- критерии выбора модулей (компонентов) ПО, подлежащих контролю целостности;
- описание процедуры контроля целостности исходного кода ПО.
#### 5.14.3.2 Описание модели управления доступом к исходному коду ПО должно включать:
- перечень сотрудников, их права и обязанности при разработке ПО;
- описание выбранной модели управления доступом и используемых инструментов управления доступом.
#### 5.14.3.3 Результаты выполнения контроля целостности собственного исходного кода должны обеспечивать соответствие требованиям регламента доступа к исходному коду ПО и обеспечения его целостности и позволять сделать однозначный вывод о целостности собственного исходного кода.

## 5.15 Обеспечение безопасности используемых секретов

### 5.15.2 Требования к реализации

#### 5.15.2.1 Разрабатывать регламент использования секретов.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик безопасности как кода в репозитории управления ИТ-инфраструктурой. Проверка наличия в этих правилах жестко задекларированных технических ограничений, описывающих регламент: запрета на коммит секретов в коде, правил обязательной ротации, требований к длине/сложности ключей и перечня разрешенных серверов хранения секретов.

#### 5.15.2.2 Использовать секреты.
**Обоснование:** Проверка наличия интеграции исходного кода и CI/CD-пайплайнов с выделенным менеджером секретов через динамическое извлечение переменных во время сборки и развертывания. Проверка наличия и результатов регулярного автоматического сканирования репозиториев на отсутствие жестко закоммиченных секретов в открытом виде в коде, конфигурациях и логах сборки. Проверка наличия включенной функции маскирования чувствительных данных в настройках CI/CD-платформы для предотвращения утечки токенов в логи выполнения задач.

#### 5.15.2.3 Проверять код и конфигурационные файлы ПО на предмет включения секретов для вносимых изменений в ПО.
Примечание — Допускается реализовывать проверку безопасности используемых секретов средствами статического или композиционного анализа.
**Обоснование:** Проверка наличия и обязательного запуска инструментов автоматического сканирования секретов на этапе Pre-commit или в рамках каждого Pull/Merge Request для блокировки внесения изменений, содержащих секреты. Проверка наличия и результатов выполнения правил PaC, запрещающих коммиты с файлами, содержащими приватные ключи, токены или пароли. Проверка наличия цифровых следов, подтверждающих, что ни одно изменение не было влито в защищенные ветки без прохождения автоматического контроля на наличие секретов.

#### 5.15.2.4 Для хранения, управления и предоставления секретов использовать систему управления секретами.
**Обоснование:** Проверка наличия развернутой и активной корпоративной системы управления секретами в ИТ-инфраструктуре компании. Проверка конфигурационных манифестов на предмет интеграции приложений с этой системой через механизмы инжекции или через обращение к API менеджера секретов вместо использования локальных конфигурационных файлов с открытым текстом. Проверка наличия и результатов автоматического аудита логов самой системы управления секретами, фиксирующих факты выдачи, отзыва и ротации токенов доступа для легитимных микросервисов и сред сборки.

### 5.15.3 Артефакты реализации требований
#### 5.15.3.1 Регламент использования секретов может содержать следующие сведения:
- обязанности сотрудников и их роли при использовании секретов;
- основные принципы использования секретов;
- зоны ответственности подразделений и сотрудников в части использования секретов;
- порядок предоставления доступа к секретам;
- типы секретов, сроки их эксплуатации, действия при компрометации;
- порядок формирования и хранения секретов;
- порядок ротации секретов;
- требования к системам хранения секретов.
#### 5.15.3.2 Описание реализации процедуры использования секретов может включать следующие сведения:
- порядок подписи исполняемого кода ПО (например, с использованием цифровых сертификатов);
- порядок подписи исходного кода (например, с использованием цифровых сертификатов).

## 5.16 Использование инструментов композиционного анализа

### 5.16.2 Требования к реализации

#### 5.16.2.1 Разработать регламент композиционного анализа.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик безопасности как кода в репозитории управления ИТ-инфраструктурой и качеством кода. Проверка наличия в этих правилах жестко задекларированных технических ограничений, описывающих регламент композиционного анализа: перечня обязательных для сканирования типов сторонних компонентов (библиотек, пакетов, Docker-образов), порогов критичности уязвимостей для блокировки сборки, списка запрещенных типов лицензий и требований к периодичности сканирования зависимостей.

#### 5.16.2.2 Формировать перечень зависимостей ПО.
**Обоснование:** Проверка наличия и автоматической генерации спецификации программных компонентов для каждого собранного репозитория и релиза ПО. Проверка наличия актуальных файлов фиксации зависимостей в системе контроля версий на момент сборки. Проверка наличия цифровых следов из SCA-систем, содержащих полный структурированный перечень транзитивных и прямых сторонних библиотек, используемых в составе программного обеспечения.

#### 5.16.2.3 Контролировать и актуализировать перечень зависимостей ПО в соответствии с регламентом композиционного анализа на предмет наличия известных уязвимостей.
**Обоснование:** Проверка наличия и результатов выполнения автоматических задач композиционного анализа в CI/CD-пайплайнах при каждом изменении кода или по регулярному расписанию. Проверка наличия в логах сборки и SCA-системах цифровых следов сверки текущих версий библиотек с актуальными базами данных известных уязвимостей. Проверка наличия срабатывания настроенных порогов блокировки, подтверждающих автоматическую остановку пайплайна или отправку алертов при обнаружении критических уязвимостей, нарушающих установленные в PaC лимиты безопасности.

#### 5.16.2.4 Осуществлять анализ заимствованных компонентов, составляющих поверхность атаки, на предмет наличия известных уязвимостей при сборке (непосредственно перед сборкой) ПО (модулей ПО, компонентов ПО).
**Обоснование:** Проверка наличия и обязательного выполнения шага SCA-сканирования в конфигурационных файлах пайплайна, расположенного строго в цепочке шагов перед финальной сборкой бинарных файлов или Docker-образов. Проверка наличия цифровых следов, подтверждающих, что проверка сторонних библиотек утилитами завершилась успешно непосредственно перед запуском команд компиляции и упаковки пакета. Проверка наличия и результатов отработки правил автоматического прерывания сборки при обнаружении незакрытых уязвимостей в заимствованных компонентах, что исключает попадание уязвимого кода в итоговый артефакт.

#### 5.16.2.5 Применять корректирующие воздействия по результатам анализа заимствованных компонентов на предмет наличия известных уязвимостей.
**Обоснование:** Проверка наличия автоматических задач в таск-трекере, созданных через API систем композиционного анализа при обнаружении уязвимостей, содержащих цифровые следы назначения ответственных и сроков устранения. Проверка наличия в репозитории коммитов с обновлением версий библиотек в файлах фиксации зависимостей, связанных с номерами исправленных дефектов. Проверка наличия цифровых следов (выписок из БД или JSON-отчетов) применения компенсирующих мер (например, правил виртуального патчинга в WAF/IDS или конфигураций исключений в файлах .trivyignore), снабженных обязательным техническим обоснованием и согласованных ИБ-службой через PR.

### 5.16.3 Артефакты реализации требований
#### 5.16.3.1 Регламент композиционного анализа должен содержать следующие сведения:
- обязанности сотрудников и их роли при проведении композиционного анализа;
- правила отслеживания уязвимостей для заимствованных компонентов, участвующих в сборке ПО;
- правила проведения анализа заимствованных компонентов на предмет наличия известных уязвимостей;
- правила принятия компенсирующих и защитных мер по противодействию выявленным угрозам безопасности в цепочке поставки сторонних компонентов;
- периодичность проведения композиционного анализа в соответствии с установленными практиками сборки ПО.
#### 5.16.3.2 Перечень зависимостей ПО должен включать следующие сведения:
- перечень модулей (компонентов) заимствованного ПО с указанием их версий;
- источник (поставщик) модулей (компонентов) заимствованного ПО.
#### 5.16.3.3 Результаты контроля актуальности перечня зависимостей ПО должны включать следующие сведения:
- описание процедуры контроля перечня зависимостей ПО и его актуализации;
- описание инструментов контроля актуальности перечня зависимостей ПО;
- журналы регистрации событий, связанных с контролем актуальности перечня зависимостей ПО, а также связанных с обновлениями модулей (компонентов) заимствованного ПО, участвующих в сборке ПО.
#### 5.16.3.4 Результаты анализа заимствованных компонентов должны содержать следующие сведения:
- сведения о наличии/отсутствии известных уязвимостей в заимствованных компонентах;
- сведения о критичности выявленных уязвимостей в заимствованных компонентах.
#### 5.16.3.5 Результаты применения корректирующих воздействий по устранению уязвимостей в зависимостях ПО могут содержать:
а) для ПО с закрытыми исходными текстами (проприетарного ПО):
1. результаты анализа применимости и реализуемости уязвимости;
2. результаты обращения к поставщику (разработчику) уязвимых модулей (компонентов) ПО по поводу их обновления;
3. результаты обновления зависимых компонентов ПО по мере поступления обновлений от поставщика (разработчика);
б) для ПО с открытыми исходными текстами:
1. результаты анализа применимости и реализуемости уязвимости;
2. результаты попыток обновления зависимых компонентов, в случае невозможности обновления путем обновления версии - применения собственного механизма исправления.

Проверка наличия цифровых следов автоматической генерации алертов в SIEM-системе при обнаружении любых несанкционированных изменений в критической инфраструктуре разработки, способных повлиять на чистоту собираемого ПО.

#### 5.17.2.5 Осуществлять анализ кода ПО, полученного через цепочки поставок, на предмет внедрения вредоносного программного обеспечения.
**Обоснование:** Проверка наличия и обязательного выполнения шагов антивирусного сканирования и динамического/песочного анализа (Sandbox) для всех внешних компонентов и пакетов, скачиваемых через цепочки поставок, перед их помещением в локальный репозиторий артефактов. Проверка наличия интеграции сборочной среды с базами данных поведенческого и репутационного анализа пакетов (например, систем класса Software Supply Chain Security) для автоматической проверки манифестов зависимостей на признаки атак типа Typosquatting (опечатки в именах), Dependency Confusion (подмена внутренних пакетов публичными) или наличие вредоносного кода в скриптах жизненного цикла (preinstall/postinstall скрипты). Проверка наличия цифровых следов (логов сканирования, вердиктов песочниц и отчетов SCA-утилит) и настроенных правил Policy as Code (Quality Gates), автоматически блокирующих сборку при обнаружении вредоносной активности или аномального поведения в заимствованном коде.

- описание внутренних процессов, зависящих от сторонних поставщиков;

- описание компонентов, являющихся частью разрабатываемого ПО, которые поставляются или заимствуются от сторонних поставщиков.

- перечень поставщиков с указанием поставляемых продуктов (услуг);
- сведения о заключенных договорах со сторонними поставщиками, включающие информацию о поставляемых продуктах (услугах), сроках начала и окончания договоров, иную информацию.
#### 5.17.3.3 Сведения о критичных и вероятных с точки зрения внедрения недекларированных возможностей элементах инфраструктуры (компонентах инфраструктуры разработки ПО, зависящих от сторонних поставщиков) должны содержать следующую информацию:
- перечень элементов инфраструктуры разработчика, воздействие на которые может повлиять на возникновение недекларированных возможностей в ПО;
- информацию о поставщиках продуктов (услуг) для указанных в перечне элементов инфраструктуры разработчика.
#### 5.17.3.4 Результаты контроля использования предсобранного поставщиком ПО должны содержать информацию, позволяющую определить наличие предсобранных поставщиком ПО компонентов и осуществить их идентификацию (по свойствам файлов, контрольным суммам файлов и т.п.).

## 5.18 Функциональное тестирование

### 5.18.2 Требования к реализации

#### 5.18.2.1 Разработать план функционального тестирования.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик автоматического контроля качества (Quality Gates и правил Policy as Code) в репозитории управления тестированием, которые регламентируют структуру и наполнение тест-планов. Проверка наличия и результатов выполнения автоматических тестов в CI/CD-пайплайне (например, джоб автотестов JUnit, PyTest, Selenium), жестко связанных через API с требованиями в таск-трекере (Jira, Youtrack) для автоматического расчета и валидации покрытия функционала тестами (Test Coverage >= X%). Проверка наличия цифровых следов (JSON-отчетов Allure, JUnit XML-логов, метрик SonarQube), фиксирующих прохождение автоматических проверок на соответствие заложенному тест-плану и блокирующих релиз в случае падения критических функциональных сценариев.

#### 5.18.2.2 Проводить функциональное тестирование, по результатам тестирования разрабатывать отчеты о выполненном функциональном тестировании.
**Обоснование:** Проверка наличия и результатов выполнения автоматических этапов (Jobs) запуска тестовых сценариев (Unit, Integration, E2E, UI-тестов) в конфигурационных файлах пайплайнов (.gitlab-ci.yml, Jenkinsfile) при каждой сборке релиза. Проверка наличия автоматически сгенерированных артефактов и цифровых следов тестирования — структурированных отчетов о прохождении тестов (Allure Report, JUnit XML, Cucumber JSON, отчеты SonarQube), сохраненных в сборочной среде или специализированном хранилище. Проверка наличия интеграции через API между CI/CD-платформой и системой управления тестированием (TMS: Test IT, Allure TestOps, Jira Zephyr) для автоматической фиксации результатов прогона (Run Status: Passed/Failed) и автоматического перевода статусов задач по дефектам в таск-трекере.

#### 5.18.2.3 При проведении функционального тестирования выполнять тестирование на уровне модулей (компонентов), подсистем, всего ПО в целом.
**Обоснование:** Проверка наличия разделения тестовых сценариев по иерархическим уровням в конфигурационных файлах пайплайнов (.gitlab-ci.yml, Jenkinsfile), подтверждающего последовательный или параллельный запуск различных типов тестов: модульных (Unit), интеграционных/подсистемных (Integration) и сквозных для всего ПО (E2E/System/UI). Проверка наличия в репозитории кода и сборочных инструкциях (например, pom.xml, package.json, pytest.ini) отдельных команд и тегов для изоляции запуска каждого уровня тестирования. Проверка наличия цифровых следов — раздельных структурированных отчетов (JUnit XML, Allure) и метрик покрытия кода (Code Coverage), собираемых отдельно для уровня модулей (например, через Jacoco/Istanbul в SonarQube) и для уровня подсистем/всего ПО (через API-тесты Postman/Newman, Selenium, Playwright).

#### 5.18.2.4 Регистрировать ход проведения тестирования.
**Обоснование:** Проверка наличия включенного логирования процесса выполнения тестов (Test Execution Logging) во всех сборочных конфигурациях и скриптах запуска фреймворков тестирования (pytest, jest, junit). Проверка наличия цифровых следов — сырых логов (Console Output / Job Trace) в CI/CD-платформе, содержащих построчную фиксацию хода тестирования (детализированные шаги setup, teardown, замеры времени выполнения каждого тест-кейса, стектрейсы ошибок). Проверка наличия автоматической отправки метаданных и логов прогона через API в централизованное хранилище логов (SIEM, Elasticsearch, OpenSearch) или специализированные TMS-системы (Allure TestOps, Test IT) с установленной политикой защиты записей от изменения (Retention Policy/WORM), гарантирующей неизменность истории тестирования.

#### 5.18.2.5 Организовывать процесс исправления выявленных в ходе тестирования ошибок с использованием системы управления ошибками.
**Обоснование:** Проверка наличия настроенной двусторонней интеграции через API между фреймворками автоматического тестирования (или TMS, такими как Test IT, Allure TestOps) и корпоративной системой управления ошибками/таск-трекером (Jira, Kaiten, Youtrack). Проверка наличия цифровых следов автоматического создания дефектов (Issues/Tickets) в таск-трекере, генерируемых пайплайном при падении автотестов, с автоматическим заполнением шагов воспроизведения, логов ошибки (Stacktrace) и назначения критичности. Проверка наличия правил Policy as Code (Quality Gates), контролирующих жизненный цикл задач: автоматический запрет на закрытие релизного пайплайна или перевод задачи в статус «Готово к деплою» при наличии в системе управления ошибками открытых дефектов безопасности и блокирующих багов, связанных с данной сборкой.

### 5.18.3 Артефакты реализации требований
#### 5.18.3.1 План функционального тестирования должен содержать следующие сведения:
- обязанности сотрудников и их роли при проведении функционального тестирования;
- описание тестового стенда (тестовой среды);
- описание сценариев тестирования для каждой функциональной возможности ПО, включающее формулировку функциональных требований, выполняемые действия по оценке, ожидаемые результаты тестирования и критерии успешного прохождения проверок;
- критерии выполнения повторного тестирования;
- критерии завершения и остановки тестирования.
#### 5.18.3.2 Отчет по результатам функционального тестирования должен содержать, как минимум, следующую информацию:
- описание тестируемого ПО (версии ПО/модулей (компонентов) ПО, номера (идентификаторы) сборок ПО/модулей (компонентов) ПО, системные требования к тестируемому ПО) и его среды функционирования для каждого выполненного сценария тестирования;
- перечень выполненных сценариев тестирования и последовательность их выполнения;
- перечень выполненных действий и ограничений (описание отдельных аспектов, которые не проверялись);
- описание полученных результатов, перечень обнаруженных и исправленных ошибок;
- выводы по результатам тестирования.
В отчетах по результатам функционального тестирования должна содержаться информация, позволяющая идентифицировать выполненные функциональные тесты ПО на уровне модулей (компонентов), подсистем, всего ПО в целом.
#### 5.18.3.3 Журналы функционального тестирования должны содержать, как минимум, следующую регистрационную информацию:
- дату и время выполнения тестовых операций (запуск и завершение сценария тестирования);
- результат выполнения сценария тестирования;
- изменения тестируемого ПО (состава и содержания модулей ПО, компонентов ПО, функциональных подсистем ПО и т.п.);
- возникновение любых сбоев и ошибок.
#### 5.18.3.4 Сведения системы управления ошибками должны содержать, как минимум, регистрационную информацию о выявленных ошибках:
- дату и время тестирования, при котором была выявлена ошибка;
- тестовый сценарий;
- идентификационную информацию о модуле (компоненте) ПО, в котором выявлена ошибка;
- категорию ошибки;
- принятое решение;
- информацию о подтверждении факта наличия ошибки от разработчика;
- информацию об исправлении ошибки.

## 5.19 Нефункциональное тестирование

### 5.19.2 Требования к реализации

#### 5.19.2.1 Проводить нефункциональное тестирование в отношении ПО (модулей ПО, компонентов ПО) в объемах, определяемых разработчиком.
**Обоснование:** Проверка наличия и результатов выполнения автоматических этапов (Jobs) нефункционального тестирования (нагрузочного, стресс-тестирования, конфигурационного, тестирования отказоустойчивости или производительности) в файлах конфигурации CI/CD пайплайнов (.gitlab-ci.yml, Jenkinsfile) [health]. Проверка наличия в репозитории инфраструктурных скриптов запуска профильного инструментария (например, сценариев jmeter, k6, locust, gatling) и правил Policy as Code (Quality Gates), определяющих допустимые пороги прохождения (например, время отклика, процент ошибок HTTP, лимиты потребления CPU/RAM). Проверка наличия цифровых следов — автоматически сгенерированных отчетов, логов и метрик производительности, сохраненных в сборочной среде или выгруженных по API в системы мониторинга (Prometheus, Grafana) и TMS по итогам прогона нефункциональных сценариев.

#### 5.19.2.2 Разработать регламент нефункционального тестирования.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик безопасности и качества как кода (Policy as Code, например, правил OPA Rego, конфигурационных файлов линтеров и сборочных Quality Gates) в репозитории управления тестированием. Проверка наличия в этих правилах жестко зафиксированных технических требований и параметров, описывающих регламент нефункционального тестирования: перечня обязательных видов проверок (нагрузочное, стресс-тестирование, стабильность, отказоустойчивость), критериев успешности прохождения (Performance Budgets, лимиты на Error Rate, максимальный Response Time, SLA/SLO) и правил автоматической блокировки продвижения сборки по пайплайну в случае их невыполнения.

#### 5.19.2.3 Проводить нефункциональное тестирование с целью выявления локальных и сетевых интерфейсов взаимодействия с ПО (модулями ПО, компонентами ПО) пользователя и взаимодействий модулей (компонентов) ПО между собой, средой функционирования и внешними объектами.
**Обоснование:** Проверка наличия и автоматического выполнения шагов динамического анализа архитектуры, сканирования портов, фаззинга и анализа сетевого трафика (например, с использованием OWASP ZAP, Nmap, Wireshark/Tshark, OpenAPI/Swagger-линтеров) на этапах нефункционального или интеграционного тестирования в CI/CD-пайплайне. Проверка наличия в репозитории конфигурационных файлов (манифестов Kubernetes/Docker Compose, схем Service Mesh, конфигураций API Gateway), описывающих сетевые периметры взаимодействия модулей. Проверка наличия цифровых следов — автоматически сгенерированных отчетов о сетевом картировании (Network Mapping/Attack Surface), трассировок вызовов (Jaeger/Zipkin-логов) и слепков открытых сетевых/локальных интерфейсов взаимодействия (Socket/IPC/IPC logs), подтверждающих полный аудит реальной поверхности атаки и межмодульных связей приложения перед релизом.

#### 5.19.2.4 Осуществлять выполнение нефункциональных тестов, в том числе имитирующих действия потенциального нарушителя.
**Обоснование:** Проверка наличия и автоматического запуска специализированных инструментов тестирования на проникновение и симуляции атак (например, OWASP ZAP, Nikto, TLS-сканеров, утилит для проведения DoS/DDoS-атак типа Slowloris или hping3) в рамках этапов тестирования безопасности (Security Testing) в CI/CD-пайплайне. Проверка наличия в репозитории конфигурационных сценариев, имитирующих деструктивные действия нарушителя: фаззинг-тестирования сетевых пакетов (например, с помощью утилит American Fuzzy Lop/AFL, Peach Fuzzer) и отправки некорректных или переполняющих буфер данных на открытые интерфейсы приложения. Проверка наличия цифровых следов — логов и структурированных отчетов (JSON/HTML вердиктов сканеров безопасности и фаззеров), фиксирующих реакцию ПО, его устойчивость к деструктивным воздействиям и подтверждающих успешное прохождение установленных ИБ-порогов (Quality Gates).

#### 5.19.2.5 Осуществлять корректировку описания поверхности атаки, модели угроз и архитектуры ПО по результатам выполнения нефункционального тестирования.
**Обоснование:** Проверка наличия автоматических задач (Issues/Tickets) в таск-трекере (Jira, Youtrack), созданных через API систем нефункционального тестирования и сканеров безопасности при обнаружении новых интерфейсов, аномалий или уязвимостей, влияющих на архитектуру. Проверка наличия цифровых следов (коммитов, Pull/Merge Requests) в репозиториях управления архитектурой как кода (Architecture as Code, например, структурированных файлов architecture.json, diagram.puml) и моделирования угроз как кода (Threat Modeling as Code, например, файлов threatmodel.yaml или скриптов pytm), содержащих изменения параметров поверхности атаки [health]. Проверка наличия логов интеграционных скриптов, подтверждающих, что даты и версии актуализации файлов архитектуры и модели угроз в Git-репозитории строго следуют за датами прогонов нефункциональных тестов, в которых были зафиксированы изменения в структуре сетевых интерфейсов или логике взаимодействия ПО.

### 5.19.3 Артефакты реализации требований
#### 5.19.3.1 Регламент нефункционального тестирования должен содержать следующие сведения:
- критерии выбора версий ПО (модулей ПО, компонентов ПО), подлежащих нефункциональному тестированию, и определения периодичности тестирования;
- перечень используемых для нефункционального тестирования методов и средств;
- обязанности сотрудников и их роли при проведении нефункционального тестирования;
- описание типовых сценариев тестирования;
- описание возможностей и мотивации потенциального нарушителя в соответствии с результатами моделирования угроз разрабатываемого ПО;
- описание типовых сценариев проведения компьютерных атак для основных сценариев работы ПО (модулей ПО, компонентов ПО).
#### 5.19.3.2 Отчет по результатам нефункционального тестирования должен содержать следующую информацию:
- краткое описание тестируемого ПО и его инфраструктуры развертывания;
- описание выполненных сценариев тестирования и последовательности их выполнения;
- набор целей (модулей ПО, компонентов ПО) тестирования;
- перечень выполненных действий и ограничений (описание отдельных аспектов, которые не проверялись);
- результаты нефункционального тестирования (снимки экрана (скриншоты), рабочие файлы инструментов нефункционального тестирования и т.п.);
- выводы, включающие следующую информацию: найденные недостатки (уязвимости) программ, средства и методы их выявления, результаты оценки опасности уязвимостей, описание возможных последствий эксплуатации уязвимостей, рекомендации по устранению найденных уязвимостей.
#### 5.19.3.3 Результаты сравнения архитектуры ПО, модели угроз и описания поверхности атаки с полученными фактическими результатами, перечень необходимых изменений в указанных артефактах реализации требований (при необходимости).

## 5.20 Обеспечение безопасности при выпуске готовой к эксплуатации версии программного обеспечения

### 5.20.2 Требования к реализации

#### 5.20.2.1 Разработать регламент приемки ПО.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик безопасности и критериев качества как кода (Policy as Code / Quality Gates, например, правил OPA Rego, пороговых настроек SonarQube и плагинов сборочных линий) в репозитории управления качеством релиза. Проверка наличия в этих машиночитаемых правилах жестко зафиксированных технических критериев готовности продукта к приемке: обязательного прохождения SAST/DAST/SCA сканирований, достижения заданного процента покрытия тестами, отсутствия критических дефектов в таск-трекере и автоматического запрета на выпуск релиза при невыполнении любого из параметров.

#### 5.20.2.2 Осуществлять анализ степени влияния на безопасность ПО неустраненных ошибок. Информация о неустраненных ошибках выпускаемого ПО должна быть зафиксирована (например, в системе управления изменениями, системе отслеживания ошибок и т.п.).
**Обоснование:** Проверка наличия и структуры записей обо всех открытых уязвимостях и багах в системе управления ошибками (Jira, Youtrack, Kaiten), жестко связанных через API с конкретным релизом или тегом сборки ПО. Проверка наличия цифровых следов проведения анализа влияния (Impact Analysis) - заполненных обязательных полей дефекта (оценка критичности по CVSS/БДУ, описание векторов атаки, затронутых компонентов и потенциального ущерба) с электронным согласованием или подписью архитектора безопасности. Проверка наличия автоматического отчета (Release Notes / Security Dashboard), генерируемого из таск-трекера и содержащего полный структурированный перечень зафиксированных неустраненных ошибок выпускаемой версии ПО.

#### 5.20.2.3 Разработать регламент обеспечения целостности ПО, передаваемого пользователям.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик автоматического контроля релизных цепочек как кода (например, конфигураций HashiCorp Vault, Harbor, Jenkins/GitLab CI, правил подписи Cosign/Notary) в инфраструктурном репозитории. Проверка наличия в этих конфигурациях жестко задекларированных технических правил генерации цифровых следов целостности: требований по автоматическому расчету контрольных сумм, правил обязательной электронной подписи артефактов (пакетов, Docker-образов) доверенными ключами компании и спецификаций безопасных защищенных каналов дистрибуции ПО.

#### 5.20.2.4 Обеспечивать возможность проверки пользователями целостности ПО.
**Обоснование:** Проверка наличия автоматически генерируемых открытых файлов контрольных сумм (файлов типа .sha256, .md5) и отсоединенных цифровых подписей (файлов типа .sig, .asc), публикуемых на внешнем ресурсе дистрибуции (сайте, публичном репозитории, GitHub Releases) вместе с дистрибутивами ПО. Проверка наличия цифровых следов выполнения команд автоматической генерации хэшей и подписей (например, вызовов sha256sum, gpg --sign, cosign sign) в логах релизного пайплайна CI/CD непосредственно в момент публикации артефактов. Проверка наличия на ресурсе загрузки ПО доступной для пользователя технической инструкции по верификации целостности (описания команд certutil, sha256sum, gpg --verify) и публичного ключа подписи компании.

### 5.20.3 Артефакты реализации требований
#### 5.20.3.1 Регламент приемки ПО должен содержать следующие сведения:
- обязанности сотрудников и их роли при проведении приемки ПО;
- описание типовых сценариев приемки ПО перед предоставлением его пользователям.
#### 5.20.3.2 Результаты анализа влияния на безопасность ПО неустраненных ошибок должны включать следующие сведения:
- перечень выявленных несоответствий;
- принятые решения по устранению несоответствий;
- принятые решения по результатам анализа о влиянии на безопасность ПО неустраненных ошибок.
#### 5.20.3.3 Регламент обеспечения целостности ПО, передаваемого пользователям, должен содержать:
- перечень мер, реализуемых разработчиком ПО с целью обеспечения возможности проверки целостности ПО пользователями;
- порядок применения мер по обеспечению возможности проверки целостности ПО пользователями;
- порядок информирования пользователей ПО о механизмах проверки целостности ПО.
#### 5.20.3.4 Результаты проверки выполнения мер по обеспечению целостности ПО.

## 5.21 Безопасная поставка программного обеспечения пользователям

### 5.21.2 Требования к реализации

#### 5.21.2.1 Разработать регламент безопасной поставки ПО пользователям.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик автоматического деплоя и дистрибуции как кода (например, манифестов GitOps, правил ArgoCD/Flux, конфигураций шлюзов доставки и защищенных CDN) в инфраструктурном репозитории. Проверка наличия в этих машиночитаемых правилах жестко зафиксированных технических требований и параметров, описывающих регламент поставки: использования исключительно шифрованных каналов передачи данных (HTTPS/SFTP), ограничений по IP-адресам для скачивания (ACL/Firewall), обязательной аутентификации пользователей и автоматической блокировки скомпрометированных каналов доставки.

#### 5.21.2.2 Фиксировать версии поставляемого пользователям ПО и соответствующей поставляемой документации.
**Обоснование:** Проверка наличия автоматической генерации уникальных идентификаторов версий (например, по стандарту SemVer и Git Commit SHA) и релизных тегов (Tags) в системе контроля версий для исходного кода и репозитории документации (Documentation as Code, например, в формате Markdown/Asciidoc). Проверка наличия цифровых следов в виде сквозного лога релизов (Release Registry или записей в СУБД/таск-трекере), где каждая версия бинарного артефакта жестко и неизменяемо связана через API с конкретным идентификатором версии соответствующего комплекта документации.

#### 5.21.2.3 Организовать хранение копий версий поставляемого пользователям ПО и соответствующей поставляемой документации.
**Обоснование:** Проверка наличия выделенного долгосрочного хранилища архивных копий (например, защищенных S3-бакетов, архивных репозиториев в Nexus/Artifactory) с включенной политикой неизменяемости данных (Object Lock / WORM) и резервного копирования. Проверка наличия цифровых следов (JSON-ответов API хранилища или логов резервного копирования), подтверждающих физическое присутствие всех ранее выпущенных версий дистрибутивов ПО и соответствующих им файлов эксплуатационной документации, а также отсутствие операций их удаления за установленный регламентом период хранения.

#### 5.21.2.4 Поставлять ПО вместе с эксплуатационной документацией, содержащей, как минимум, описание штатного функционирования ПО, параметров настроек (конфигураций) ПО и среды функционирования, действий по установке и настройке средства, как с точки зрения штатного функционирования, так и с точки зрения обеспечения безопасности.
**Обоснование:** Проверка наличия обязательного включения файлов технической и эксплуатационной документации (например, каталога docs/, файлов README.md, SECURITY.md, INSTALL.md) в состав итогового дистрибутива, архива поставки или Docker-образа при сборке. Проверка наличия результатов автоматического парсинга (линтеров и генераторов документации, таких как Sphinx, MkDocs) на присутствие в структуре документов обязательных ключевых разделов: требований к среде функционирования, инструкций по безопасной настройке (Hardening Guide), описания ролевой модели и параметров конфигурации безопасности.

### 5.21.3 Артефакты реализации требований
#### 5.21.3.1 Регламент безопасной поставки ПО пользователям должен содержать следующие сведения:
- обязанности сотрудников и их роли при осуществлении безопасной доставки ПО;
- процедуры хранения копий версий поставляемого пользователям ПО;
- процедуры снятия копий (тиражирования) поставляемого пользователям ПО;
- процедуры поставки ПО (обновлений ПО, включая обновления безопасности, предназначенных для устранения недостатков, в том числе уязвимостей);
- процедуры проверки подлинности ПО (обновлений ПО) пользователем.
#### 5.21.3.2 Сведения о версии поставляемого пользователям ПО должны быть зафиксированы в поставляемой документации (в электронном виде или на физическом носителе).
#### 5.21.3.3 Сведения о месте хранения копий (подлинников, дубликатов) версий поставляемого пользователям ПО (инсталляционных пакетов, дистрибутивных носителей) должны быть зафиксированы в документации (в электронном виде или на физическом носителе), например в регламенте безопасной поставки ПО.
#### 5.21.3.4 Сведения о поставляемой эксплуатационной документации на ПО должны быть зафиксированы (в электронном виде или на физическом носителе), например в регламенте безопасной поставки ПО, в паспорте (формуляре) ПО.

## 5.22 Обеспечение поддержки программного обеспечения при эксплуатации пользователями

### 5.22.2 Требования к реализации

#### 5.22.2.1 Разработать регламент технической поддержки.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик и правил автоматической обработки обращений как кода (например, SLA-схем, конфигурационных манифестов Service Desk систем типа Jira Service Management, Zendesk или Naumen) в репозитории администрирования ИТ-сервисов. Проверка наличия в этих машиночитаемых правилах жестко задекларированных технических регламентов: маршрутов эскалации инцидентов, градаций критичности обращений, лимитов времени на реакцию и решение заявок, а также обязательных процедур классификации инцидентов ИБ, связанных с уязвимостями ПО.

#### 5.22.2.2 Организовать работу службы технической поддержки.
**Обоснование:** Проверка наличия развернутой, активной и доступной платформы учета обращений (Service Desk / Help Desk) в ИТ-инфраструктуре компании. Проверка наличия цифровых следов ее функционирования в виде сквозного журнала зарегистрированных заявок и инцидентов (системных логов, выгрузок из СУБД по API), подтверждающих реальную регистрацию, назначение ответственных инженеров, фиксацию временных меток смены статусов и успешное автоматическое применение SLA-метрик к поступающим от пользователей запросам.

#### 5.22.2.3 Разработать процедуру оповещения пользователей о выпуске обновлений (включая обновления безопасности) и необходимости их установки.
**Обоснование:** Проверка наличия и работоспособности настроенных автоматизированных каналов массового оповещения, интегрированных по API с релизным контуром (например, скриптов отправки Email-рассылок, Telegram/Slack-ботов, RSS-лент или систем push-уведомлений внутри ПО). Проверка наличия цифровых следов (логов серверов отправки почты, JSON-ответов API шлюзов рассылки) с успешными статусами доставки сообщений, содержащих информацию о выходе новых версий, списки закрытых уязвимостей (Security Changelog) и ссылки на защищенные репозитории обновлений.

#### 5.22.2.4 Организовывать обучение специалистов службы технической поддержки работе с поставляемым ПО, особенностям его установки и функционирования, ограничениям и указаниям по эксплуатации.
**Обоснование:** Проверка наличия и активности учетных записей сотрудников службы технической поддержки в корпоративной системе дистанционного обучения (LMS, например, Moodle, WebTutor) на специализированных курсах по архитектуре и безопасности поставляемого ПО. Проверка наличия цифровых следов прохождения обучения (JSON/XML отчетов LMS-системы, выгрузок из баз данных), содержащих ФИО инженеров, даты завершения курсов, результаты прохождения проверочных автоматических тестов и статусы выданных электронных сертификатов.

#### 5.22.2.5 Разработать процедуру информирования пользователей ПО о выявленных уязвимостях и способах реализации мер по их нейтрализации до разработки обновлений безопасности, устраняющих уязвимость, по установленным каналам взаимодействия.
**Обоснование:**  Проверка наличия зафиксированных в таск-трекере или системе публикации (Confluence, Wiki, корпоративный портал) шаблонов и автоматизированных воркфлоу для оперативного выпуска бюллетеней безопасности (Security Advisories / Workarounds). Проверка наличия цифровых следов (логов публикации, истории коммитов в репозиторий публичных уведомлений) отправки пользователям временных компенсирующих мер и технических рекомендаций по ручной нейтрализации угроз (например, правил для WAF/IDS, изменений конфигурационных файлов ПО или сетевых ограничений) в период до выпуска официального патча [health].

### 5.22.3 Артефакты реализации требований
#### 5.22.3.1 Регламент технической поддержки должен содержать следующие сведения:
- обязанности сотрудников и их роли при оказании технической поддержки;
- описание организации службы технической поддержки: режим работы, сроки оказания услуг по технической поддержке пользователей, иная информация об организации службы технической поддержки;
- используемые инструменты;
- описание процедуры взаимодействия службы технической поддержки с пользователями (способы получения обращений пользователей, процесс обработки поступающих сообщений и др.);
- описание процедур оповещения пользователей о выпуске обновлений (включая обновления безопасности) и необходимости их установки;
- описание процедур информирования пользователей ПО о выявленных уязвимостях и способах реализации мер по их нейтрализации до разработки обновлений безопасности, устраняющих уязвимость, по установленным каналам взаимодействия;
- информацию об обучении сотрудников службы технической поддержки.
#### 5.22.3.2 Артефактами реализации требований, подтверждающими наличие технической поддержки, могут являться записи о наличии должностей сотрудников технической поддержки в штатном расписании организации, документированные факты оказания конкретных услуг по технической поддержке пользователей, иные факты и документированные материалы.
#### 5.22.3.3 Артефакты реализации требований, подтверждающие наличие внедренных процессов оповещения пользователей, должны содержать информацию об используемых каналах взаимодействия с пользователями при выпуске обновлений (включая обновления безопасности) и необходимости их установки.
#### 5.22.3.4 Артефакты реализации требований, подтверждающие наличие процессов обучения специалистов службы технической поддержки, могут содержать информацию о пройденных семинарах, вебинарах, курсах или иную информацию, подтверждающую умения и знания специалистов службы технической поддержки, необходимые для работы с поставляемым ПО, его особенностям установки и функционирования, ограничениями и указаниями по эксплуатации.
#### 5.22.3.5 Артефакты реализации требований, подтверждающие наличие процессов информирования пользователей ПО о выявленных уязвимостях, должны содержать информацию об используемых каналах взаимодействия с пользователями и способах реализации мер по их нейтрализации до разработки обновлений безопасности, устраняющих уязвимость.

## 5.23 Реагирование на информацию об уязвимостях

### 5.23.2 Требования к реализации

#### 5.23.2.1 Разработать регламент реагирования на информацию об уязвимостях.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик и правил автоматического реагирования на инциденты (Incident Response Playbooks) как кода в репозитории управления информационной безопасностью (например, в форматах SOAR-сценариев, правил OPA Rego или автоматизированных воркфлоу). Проверка наличия в этих машиночитаемых правилах жестко зафиксированных технических метрик и регламентов: временных рамок (SLA) локализации угроз, критериев автоматического назначения ответственных аналитиков ИБ (Vulnerability Handlers), маршрутов эскалации и перечня автоматических триггеров для запуска процедур патчинга или изоляции уязвимых сред.

#### 5.23.2.2 Осуществлять обработку поступающих запросов от пользователей (через службу технической поддержки, по иным каналам взаимодействия) с последующим анализом ошибок функционирования на предмет наличия уязвимостей (в случае получения таких запросов).
**Обоснование:** Проверка наличия настроенных сквозных связей через API между платформой поддержки (Service Desk) и экспертными инструментами ИБ (например, сканерами уязвимостей, отладчиками или системами анализа кода). Проверка наличия цифровых следов передачи обращений пользователей о сбоях на анализ в контур безопасности: автоматического создания связанных ИБ-задач, логов работы автоматических парсеров пользовательских дампов памяти/логов на признаки эксплуатации уязвимостей, а также результатов проверки подозрительных участков кода статическими или динамическими анализаторами (SAST/DAST).

#### 5.23.2.3 При обработке поступающих запросов и при последующем анализе использовать средства автоматизации (например, систему управления изменениями, систему отслеживания ошибок, систему управления задачами и т.п.).
**Обоснование:** Проверка наличия и активного использования развернутых систем автоматизации жизненного цикла дефектов (Jira, Youtrack, Kaiten, GitLab Issues), интегрированных по API со всеми смежными ИТ-платформами. Проверка наличия цифровых следов сквозной автоматизации процесса обработки уязвимостей: логов автоматического перевода статусов задач (например, от «Заявка принята» до «Передано в разработку»), автоматического назначения тегов (например, security-vulnerability, CVE-ID), автоматического контроля сроков решения по SLA и оповещения участников процесса без ручного вмешательства.

#### 5.23.2.4 Осуществлять анализ информации о найденных уязвимостях в ПО на предмет подтверждения наличия/отсутствия уязвимостей и принимать решение о необходимости их устранения по результатам оценки.
**Обоснование:** Проверка наличия в системе управления задачами (таск-трекере) заполненных карточек верификации уязвимостей, содержащих цифровые следы подтверждения дефекта — отчетов утилит автоматической валидации (например, PoC-скриптов, логов фаззеров, результатов работы DAST или верифицированных алертов от систем интерактивного анализа IAST). Проверка наличия в СУБД таск-трекера или ИБ-портала зафиксированных решений по итогам анализа уязвимости: признания уязвимости ложным срабатыванием (False Positive) со ссылкой на техническое обоснование или присвоения статуса (Confirmed) с автоматической передачей на этап планирования исправления.

#### 5.23.2.5 Осуществлять оценку актуальности и критичности уязвимости с точки зрения безопасности ПО (в случае получения информации об уязвимости ПО из внешнего источника) и принимать решение о необходимости ее устранения по результатам оценки.
**Обоснование:** Проверка наличия интеграции таск-трекера или Vulnerability Management платформы через API со сторонними базами знаний и регуляторами (БДУ ФСТЭК России, NVD, Vulners, GitHub Advisory) для автоматического обогащения карточки уязвимости данными о ее критичности (базовый скоринг CVSS, наличие публичных эксплойтов, тип вектора атаки). Проверка наличия цифровых следов расчета локального контекста уязвимости (Environmental Score) — заполненных полей оценки доступности уязвимого компонента из внешней сети, наличия компенсирующих мер (WAF, IPS) и автоматического присвоения итогового приоритета устранения на основе правил Policy as Code.

### 5.23.3 Артефакты реализации требований
#### 5.23.3.1 Регламент реагирования на информацию об уязвимостях должен содержать:
- обязанности сотрудников и их роли при реагировании на информацию об уязвимостях ПО;
- правила реагирования на информацию об уязвимостях;
- правила оценки актуальности и критичности уязвимости с точки зрения безопасности ПО;
- периодичность проведения поиска известных (подтвержденных) уязвимостей в общедоступных источниках информации об уязвимостях ПО.
#### 5.23.3.2 Артефакты реализации требований, подтверждающие получение и обработку запросов от пользователей, должны содержать следующие сведения:
- информацию о запросах пользователей об ошибках (уязвимостях) ПО (дата, время запроса, идентификатор пользователя, статус запроса);
- результат анализа ошибок функционирования на предмет наличия уязвимостей.
#### 5.23.3.3 Артефакты реализации требований, подтверждающие выполнение анализа информации о найденных уязвимостях в ПО, должны содержать следующие сведения:
- информацию о результатах тестирования ПО на предмет применимости информации об уязвимости ПО;
- проект (шаблон) ответа пользователям на запросы пользователей об ошибках (уязвимостях) ПО (о применимости информации о найденных уязвимостях);
- решение по результатам анализа информации о найденных уязвимостях в ПО.
#### 5.23.3.4 Артефакты реализации требований, подтверждающие выполнение оценки актуальности и критичности уязвимости с точки зрения безопасности, должны содержать следующие сведения:
- информацию об оценке актуальности уязвимости;
- информацию об оценке уровня критичности уязвимости ПО;
- решение по результатам анализа актуальности и критичности уязвимости.

## 5.24 Поиск уязвимостей в программном обеспечении при эксплуатации

### 5.24.2 Требования к реализации

#### 5.24.2.1 Разработать регламент поиска ошибок и уязвимостей в ПО при его эксплуатации.
**Обоснование:** Проверка наличия и применения конфигурационных файлов политик безопасности как кода (Policy as Code, например, правил OPA Rego, расписаний CronJobs в Kubernetes/GitLab и конфигураций сканеров уязвимостей) в репозитории управления ИБ-инфраструктурой. Проверка наличия в этих машиночитаемых правилах жестко задекларированных технических требований и параметров, описывающих регламент поиска: графиков автоматического сканирования работающих сред, перечня обязательных утилит (DAST, баз данных уязвимостей, лог-анализаторов) и правил автоматического заведения инцидентов при обнаружении аномалий или новых векторов атак на эксплуатируемое ПО.

#### 5.24.2.2 Актуализировать информацию об уязвимостях ПО из открытых источников на регулярной основе на всем протяжении срока действия его технической поддержки: выполнять поиск в открытых источниках информации об уязвимостях самого ПО и его сторонних компонентов.
**Обоснование:** Проверка наличия и регулярного выполнения автоматических скриптов синхронизации (Cron-задач), интегрированных по API с внешними базами данных уязвимостей (БДУ ФСТЭК России, NVD, Vulners, GitHub Advisory) [health]. Проверка наличия цифровых следов (JSON-логов, записей в БД систем класса Vulnerability Management или Dependency Track), подтверждающих успешный сбор, парсинг и сопоставление свежих CVE/БДУ-идентификаторов со списком используемых в эксплуатируемом ПО сторонних библиотек (SBOM) и метаданными собственного ПО за последние 24 часа.

#### 5.24.2.3 Проводить проверки кода ПО и настроек конфигураций ПО на регулярной основе на всем протяжении срока действия его технической поддержки с целью поиска ошибок и уязвимостей.
**Обоснование:** Проверка наличия и результатов выполнения периодических автоматических задач сканирования (Scheduled/Nightly Pipelines) в CI/CD-системе или на специализированных платформах (SonarQube, Checkmarx, PT Application Inspector), настроенных для проверки актуальных production-веток кода. Проверка наличия цифровых следов регулярного аудита — логов выполнения инструментов статического анализа (SAST) и сканеров конфигурации инфраструктуры (IaC-линтеров типа Checkov, Tfsec, Kubescape), запускаемых по расписанию для выявления скрытых ошибок, накопленного технического долга и деградации уровня безопасности кода в процессе эксплуатации.

#### 5.24.2.4 Оценивать выявленные ошибки на предмет наличия уязвимостей.
**Обоснование:** Проверка наличия настроенной интеграции через API между системами мониторинга ошибок в реальном времени (Sentry, GlitchTip, ELK) и корпоративной платформой ИБ / таск-трекером. Проверка наличия цифровых следов автоматической или автоматизированной классификации сбоев: логов работы экспертных правил или ИБ-скриптов, которые анализируют трейсы ошибок (Stacktraces), аномальные падения (Crashes) и необработанные исключения (Uncaught Exceptions) на предмет наличия признаков уязвимостей (например, Buffer Overflow, SQL Injection, десериализация небезопасных данных) с последующим присвоением задаче тега security-risk.

### 5.24.3 Артефакты реализации требований
#### 5.24.3.1 Регламент поиска ошибок и уязвимостей в эксплуатирующемся ПО должен содержать:
- обязанности сотрудников и их роли при поиске ошибок и уязвимостей в эксплуатирующемся ПО;
- правила поиска известных (подтвержденных) уязвимостей в общедоступных источниках информации об уязвимостях ПО, его программных компонентов и сред его функционирования;
- состав проводимых проверок и периодичность их проведения на протяжении всего срока действия технической поддержки ПО для каждой версии ПО.
#### 5.24.3.2 Регулярные отчеты по результатам проводимых проверок, в которые включается информация об исправлении найденных ошибок, выпуска обновлений ПО и доставки обновлений ПО пользователям.

## 5.25 Обеспечение безопасности при выводе программного обеспечения из эксплуатации

### 5.25.2 Требования к реализации

#### 5.25.2.1 Разработать регламент вывода ПО из эксплуатации.
**Обоснование:** Проверка наличия и применения файлов конфигурации политик удаления ресурсов как кода (Policy as Code, например, правил OPA Rego, сценариев автоматического декоммишена в Ansible/Terraform или манифестов удаления в ArgoCD) в репозитории управления ИТ-инфраструктурой. Проверка наличия в этих машиночитаемых правилах жестко зафиксированных технических требований и параметров, описывающих регламент вывода из эксплуатации: процедур автоматического отзыва TLS/SSL-сертификатов, деактивации учетных записей (IAM/Active Directory), удаления DNS-записей, гарантированного уничтожения данных (Data Wiping) в хранилищах и архивации исходного кода с переводом репозиториев в режим Read-Only.

#### 5.25.2.2 Информировать пользователя о планах прекращения технической поддержки ПО (версии ПО) и своевременно уведомлять об этом.
**Обоснование:** Проверка наличия настроенных автоматизированных контуров и скриптов рассылки уведомлений (End-of-Life / End-of-Support), интегрированных по API с базой данных клиентов и реестром версий ПО. Проверка наличия цифровых следов (JSON-логов почтовых шлюзов, API-ответов сервисов отправки push-уведомлений или систем массовой рассылки), подтверждающих успешную доставку пользователям официальных сообщений о планах прекращения поддержки с указанием точных дат (микротаймстемпов) окончания жизненного цикла версии ПО. Проверка наличия автоматически обновляемых публичных файлов манифестов (например, файлов product_lifecycle.json или страниц на портале поддержки), содержащих актуальные статусы поддержки (Supported/Deprecated/EOL) для автоматического считывания внешними системами пользователей.

### 5.25.3 Артефакты реализации требований
#### 5.25.3.1 Регламент вывода ПО из эксплуатации должен содержать описание условий, при которых ПО (версию ПО) необходимо выводить из эксплуатации, обязанности сотрудников и их роли при осуществлении вывода ПО из эксплуатации ПО и порядок оповещения пользователей о планах прекращения технической поддержки ПО (версии ПО).
